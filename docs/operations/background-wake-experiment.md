# KDE/Wayland Brave focus restoration (experimental branch)

On KDE/Wayland this branch still opens a Brave wake window so the existing content script can submit the exact ChatGPT wake message. A short-lived KWin script snapshots the prior focused window and restores it only if the *new* Brave window takes focus and the user has not switched windows/desktops. This leaves Brave behind the previous application, without another browser extension, permission, native host, or keyboard injection. The window can still flash briefly; this is not a background tab and does not work when Brave is closed or ChatGPT cannot complete the wake. Outside KDE/Wayland, on KWin failure, or with `PI_LLM_GATEWAY_RESTORE_FOCUS=false`, PiLink keeps the original behavior. No real ChatGPT wake has been verified in this branch.

## What the experiment establishes

`test/background-wake-lab/` contains isolated Brave/CDP runners. `node test/background-wake-lab/run-lab.mjs` checks that `chrome.tabs.create({active:false})` can open an inactive synthetic tab without `tabs` permission. `node test/background-wake-lab/run-send-fixture.mjs` injects the **actual PiLink Wake content script** into an intercepted, entirely local ChatGPT-shaped page in an inactive headless Brave tab; it asserts `visibilityState=hidden`, `document.hasFocus()=false` and exactly one simulated send-button click, saving `send-background.png`. Both use fresh temporary browser profiles and never contact the real ChatGPT site or use the user's Brave profile. These screenshots cannot prove delivery by ChatGPT.

## A fully hidden browser tab is a different feature

1. **Authenticated trigger:** The gateway is a local Node process, not a Chrome extension. It cannot invoke `chrome.tabs.create` directly. An MV3 service worker needs a narrow, authenticated gateway→extension channel. Native Messaging would require a separately registered host, a stable extension ID in its `allowed_origins`, and the new `nativeMessaging` browser permission. Loopback polling instead requires additional localhost host permissions and careful origin, token, replay, lifecycle, and abuse protections. Do not introduce unauthenticated endpoints or DevTools remote debugging on the real browser profile.
2. **Real worker delivery:** This fixture loads a tiny extension page. Inactive `chatgpt.com` tabs may delay loading, freeze or be discarded; a background tab containing a prefilled message might never run the content script or send the message. Only a real, consented end-to-end test with the user's account and verified gateway worker contact can establish this.
3. **Lifecycle:** A successful trigger should deduplicate or clean up wake tabs without reading unrelated tabs or chat contents. Fallback to the existing foreground/manual flow must be explicit and must never synthesize a global Enter key.

The synthetic fixtures never touch the user's Brave profile or ChatGPT session. The focus restoration path is separately tested with mocked KWin signals and commands. In one operator trial of this **specific** branch, Brave did move behind the previous window but the message was not sent; the operator reports successful background sending in earlier circumstances. Do not infer that background sending is impossible from this one failed attempt or that the synthetic click proves the real site worked. The next diagnostic is the fixed-text `PiLink wake:` badge on the actual wake window: it distinguishes missing extension injection, page navigation, editor readiness, and a recorded click without sharing prompts or account contents.
